# How the public repositories keep their version pins current

Every public probityai repository names versions of the family packages it installs: a lock in `version-pins.toml`, the pages the lock holds and, in the tap, the Homebrew formulas. A release of one package used to leave the others naming the release before it until someone moved them by hand.

## The mechanism

`actions/pin-refresh` runs in each consuming repository. It moves each family lock to the newest release, rewrites the pages the lock holds, puts back any change under `.github/workflows` (Dependabot owns the Action pins there), commits on a branch named after the change and opens a pull request. How it lands depends on the token:

- **Given a GitHub App** (`app-client-id` and `app-private-key`), the action mints an installation token and opens the pull request with it. GitHub then starts the pull request's own `pull_request` run like it would for a person. The action asserts that run started on the head commit (a run held as `action_required` is a refusal), turns on auto-merge and ends. The repository's branch rules and merge queue run the full CI once, on the merge group, and land it. Head branches of earlier bumps that no open pull request uses are deleted on the next run.
- **Without an App**, the Actions `GITHUB_TOKEN` opens the pull request. The action dispatches each CI workflow on the bump branch, waits for the `workflow_dispatch` run it started, and merges, or enqueues and dispatches on the merge group, when all succeeded. A failed run leaves the pull request open with the failing run named.

`verify-pr: <number>` changes nothing: it fails unless each `ci` workflow has a `pull_request` run on that pull request's head that GitHub did not hold for approval. Run it to prove a repository's App is wired before relying on it.

Dependabot keeps manifests (`pyproject.toml`, `uv.lock`, `Cargo.toml`) and the Action pins in workflow files. History never moves: `[scan] historical`, `version-pins: keep` and `off` to `on` are read by the rewrite exactly as by the check.

## Decisions

- **No cross-repository release dispatch.** A token made by Actions cannot dispatch a workflow in another repository. Each consuming repository polls hourly instead, so a release reaches it within an hour. The check that fails closed (`registry-verify`) lets a lock lag by one release for one day, so the poll sits well inside it. A release in the same repository starts the refresh at once through `workflow_run`.
- **A bump pull request opened by `GITHUB_TOKEN` gets a `pull_request` run that never starts.** GitHub creates it held as `action_required`, with no jobs, about two seconds after the action's own dispatch. Until 17 Nov 2026 the action took the newest run on the branch as its own, read the held run, and reported a failure while its dispatched run passed: every refresh of probityai/probity from 14 to 17 Nov stopped there (#338, #349). The action now matches the `workflow_dispatch` event of the run it started.
- **An App is the path that needs no waiting.** With the Actions token the job waits up to two CI runs and dispatches them itself, and a repository whose branch rules require checks that exist only on `pull_request` events (vectors: `dco/sign-off`, governance, no-internal-drafts, identity-scan) cannot merge by itself. An App-opened pull request gets those runs from GitHub, so it lands through the repository's own rules. The App is owned by the probityai organisation and has a neutral name, because its name is printed as the author of every bump pull request in a public repository. Give each consuming workflow `app-client-id: ${{ vars.PIN_REFRESH_APP_CLIENT_ID }}` and `app-private-key: ${{ secrets.PIN_REFRESH_APP_PRIVATE_KEY }}`; the action refuses one half without the other, so a missing secret cannot fall back silently.
- **A bump already pushed is moved forward, never forced.** The bump branch is named after its diff, so an hourly run that finds the branch still open stands on it. Once the default branch moves, the same bump has another tree on the new base and a plain push of it is refused as a non-fast-forward (probityai/probity run 44161410339 on #349, 17 Nov 2026). The run then pushes a commit with the new tree whose parents are the pushed tip and the new bump, so the push is a fast-forward and the pull request's head is the bump on the current base.
- **Homebrew settles a release for a day.** `brew update-python-resources` refuses a package uploaded within the last day. A config that feeds a tap sets `[refresh] settle_hours = 25`: the lock moves only to a release at least that old, and the one-day grace grows by the same hours.
- **Brew-provided packages are not resources.** A formula that lists `depends_on "cryptography"` gets `--exclude-packages=cryptography`, so the resource blocks hold only what brew does not provide.
